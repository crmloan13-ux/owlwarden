Fix sensitive data written to a log in Fastify

A password, token, cookie, or similar value is passed to a log sink. Centralised logs are widely readable inside an organisation and often retained for months — a credential that lands there is a credential that has left the application's control.

medium likely Fastify CWE-532 · OWASP A09:2021

The vulnerable pattern in Fastify

MEDIUM likely Sensitive data written to a log A09:2021 src/server.ts:49:22 47 │ app.post('/session', async (request, reply) => { 48 │ // sensitive-data-logged: Fastify's request.log is a real log sink. 49 │ request.log.info({ password: (request.body as { password?: string }).password }) │ ~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~ sensitive value written to a log 50 │ 51 │ // sensitive-data-logged: an access token, logged the same way.

This is a real finding from the Fastify fixture in the owlwarden test suite. Logs are copied into aggregators, retained for months, and readable by anyone with access to the logging system. A credential that reaches a log has left the application's trust boundary.

The corrected handler

Use request.log with a redacted payload.

request.log.info({ event: 'login_attempt', userId })
// never: request.log.info({ password: request.body.password })

If you are not using Fastify

Log a redacted shape — an id, a boolean, a length — never the secret itself.
